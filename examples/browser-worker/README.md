# Browser Worker examples

Minimal pages and application Workers for the C++ browser-node build. These are
integration examples, separate from the Web Node dashboard application.

- `headers.html` and `headers-worker.js`: run the C++ header synchronization
  executable and display its progress.
- `headers-api.html` and `headers-api-worker.js`: use the generated asynchronous
  `HeaderSync` application binding, with Start and Stop controls.
- `headers-live-worker.js`: follow the chain, reconnect with backoff, and expose
  a bounded header window to the embedding page.
- `headers-persistent-worker.js` and `header-storage.js`: opt-in IndexedDB header
  caching, local revalidation, and storage failure fallback.

## Build and serve

Follow the [browser test build instructions](../../tests/browser-worker/README.md).
CMake writes the control artifacts under `$BUILD/tests/browser-worker`.

For the direct C++ example, copy `headers.html`, `headers-worker.js`,
`browser_headers_control.js`, and `browser_headers_control.wasm` into one serving
directory. For the application example, copy `headers-api.html`,
`headers-api-worker.js`, and the generated `browser_headers_api_control.js` and
`.wasm` pair instead. The application target requires matching external glue and
pre-JS generated by kth-tools; see the test instructions for its CMake inputs.

Serve that directory over HTTP locally or HTTPS publicly. Select a matching
network and a WebSocket peer/bridge that permits the page's exact Origin. HTTPS
pages require WSS. These examples do not provide a bridge or a remote node.

For the persistent Worker, copy `headers-persistent-worker.js` and
`header-storage.js`, and rename the matching application module pair to
`browser_headers_persistent_v1.js` and `browser_headers_persistent_v1.wasm`.
The embedding page starts it with `{type: 'start', bridge, network, capacity}`;
`stop`, `resume`, and `getHeaders` messages use the live Worker's interface.

The [test directory](../../tests/browser-worker/README.md) owns the regression
runners, fixtures and scenario-specific Workers. Its persistence runner reads
these example sources directly; the other manual runners expect the selected
page and required scenario Workers to be served together with the built module.

The Worker must await pending native operations before resetting or disposing
the client. Browser suspension or page disposal can interrupt a session; the
examples do not guarantee background execution or full block/UTXO validation.
